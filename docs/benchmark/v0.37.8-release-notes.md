# v0.37.8 fail-fast setup mutation lock

Status: reliability release. It does not change ordinary Sol-Luna routing and does not establish included-plan allowance savings.

## Problem

The setup lifecycle used atomic individual file writes but did not exclude two mutating commands from acting on the same state concurrently. A duplicate updater was observed completing in one process while another process remained alive and consumed a logical core. Read-only inspection commands should remain available during a mutation.

## Change

`install`, `update`, `migrate`, and `rollback` now acquire one non-blocking operating-system advisory lock on `<codex-home>/sol-luna-setup.lock`. A contender makes one attempt and exits with a `BUSY` setup error containing the operation and resolved lock path. Windows uses `msvcrt` first-byte locking; POSIX uses `fcntl.flock`. The handle is released on normal return and exceptions, while process termination relies on operating-system handle cleanup.

The lock path rejects symlink or reparse traversal and is revalidated after opening. The persistent lock file is coordination state, not a managed Skill asset. `preview`, `migration-preview`, and `doctor` remain lock-free and read-only.

## Evidence and limits

- Frozen visible acceptance: 6/6 passed.
- Repository suite: 451 passed, 4 skipped, one execution.
- Route-external hidden acceptance: 10/10 passed; the real Windows directory-symlink case was skipped because the host lacked symlink privilege, while lock-target, Codex-root, and nested-parent link-like rejection remained covered by deterministic tests.
- `git diff --check`: passed.
- Independent read-only implementation review: `REVIEW_PASS`.

The matched Sol-Luna economic arm was not executable because the host denied the Luna writer's exact formal-repository write permission. This release therefore makes no Sol-Luna-versus-Sol-only credit or allowance claim.
